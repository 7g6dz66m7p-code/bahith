# ADR-0003: عامل Python لمعالجة المستندات عبر BullMQ

- **الحالة:** مقبول
- **التاريخ:** 2026-11-14
- **المرحلة:** 1 (الهيكل) — المعالجة الفعلية في المرحلة 3

## السياق

استخراج النص من PDF/DOCX مع أرقام الصفحات، والتقطيع، والتضمين مهام ثقيلة وطويلة لا تصلح داخل طلب HTTP. أفضل مكتبات الاستخراج (PyMuPDF، Docling، python-docx) مكتوبة بـPython، بينما بقية المنصة TypeScript.

## القرار

1. **عامل Python مستقل** في `apps/worker` يستهلك المهام من طابور **BullMQ على Redis**. تطبيق الويب هو المنتِج الوحيد.
2. **عميل BullMQ الرسمي لـPython** (`bullmq` على PyPI، من فريق BullMQ نفسه) ليتكلم العامل بروتوكول الطابور ذاته دون جسر HTTP.
3. **عقد الطابور:** طابور واحد (`bahith-documents` افتراضياً، قابل للضبط بـ`WORKER_QUEUE`)، والمهام تُميَّز بالاسم (`system.ping` الآن، ومهام المستندات في المرحلة 3). كل حمولة تُتحقق بمخطط Pydantic يرفض الحقول الزائدة؛ اسم مهمة غير معروف أو حمولة غير صالحة = فشل بكود ثابت (`UNKNOWN_JOB`، `INVALID_PAYLOAD`).
4. **الخصوصية:** السجلات تحمل معرّف المهمة واسمها ونتيجتها فقط، ولا تحمل بيانات المهمة أبداً (مُختبَر).
5. **Prompt Injection:** العامل يعامل نص المستند بيانات فقط، ولا يملك أدوات كتابة عامة أو جلب روابط.
6. **الاتجاه للمرحلة 3:** العامل يكتب المقاطع في Postgres بدور `bahith_app` نفسه ويربط `app.workspace_id` لكل مهمة، فيخضع لـRLS مثل الويب. الملفات تُقرأ من S3 بمفتاح التخزين الوارد في المهمة.
7. **الأدوات:** `uv` للاعتماديات و`ruff` للفحص و`pytest` للاختبارات؛ `package.json` صغير في `apps/worker` يجعل Turborepo يشغّل مهامه مع البقية.

## التحقق المنفَّذ في المرحلة 1

- اختبار تكامل: مهمة تُضاف وتُستهلك عبر Redis حقيقي (Testcontainers)، ومهمة مجهولة تُوسم فاشلة بكودها.
- تحقق يدوي عابر للغتين: منتِج Node (`bullmq@6.7.6`) أضاف `system.ping` واستلم النتيجة من عامل Python (`bullmq==3.6.1`). النتيجة في تقرير المرحلة 1.

## البدائل

| البديل                                | سبب الرفض                                                                                       |
| ------------------------------------- | ----------------------------------------------------------------------------------------------- |
| المعالجة في Node (pdf.js / pdf-parse) | جودة استخراج أضعف للعربية والجداول وترتيب القراءة، ولا مقابل لـDocling.                         |
| خدمة Python بـHTTP (FastAPI)          | تحتاج مصادقة بين الخدمتين وإدارة مهلات وإعادة محاولة يدوياً؛ الطابور يعطي ذلك جاهزاً مع ضغط خلفي. |
| Celery / RQ                           | بروتوكول مختلف عن BullMQ فيحتاج المنتِج (Node) جسراً أو عميلاً غير رسمي.                           |
| Temporal أو طابور سحابي (SQS)         | تعقيد أو ارتباط بمزوّد لا يبرره MVP؛ Redis مطلوب أصلاً.                                           |

## العواقب

- **إيجابية:** أفضل مكتبات الاستخراج متاحة؛ عزل الأعطال (تعطل ملف لا يُسقط الويب)؛ توسعة العامل أفقياً مستقلة.
- **سلبية:** لغتان وسلسلتا أدوات؛ عقد الحمولة يُعرَّف مرتين (Zod في Node وPydantic في Python) ويجب إبقاؤهما متطابقين — يُغطى باختبار عقد في المرحلة 3.
- **مخاطرة:** عميل Python لـBullMQ يتأخر عن عميل Node في بعض الميزات (flows، بعض خيارات الجدولة). نلتزم بالمجموعة الأساسية (add / process / retry / backoff) ونثبّت نسختي العميلين ونعيد اختبار التوافق عند الترقية.
