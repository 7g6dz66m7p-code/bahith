# ADR-0007: هوية خاصة وجلسات موثقة قبل إتاحة البحث

- **الحالة:** مقبول — تنفيذ المرحلة الثانية
- **التاريخ:** 2026-11-14

## السياق

طلب الاستكمال الحالي يجيز متابعة المراحل المعروفة في المستودع دون انتظار موافقة
بعد كل مرحلة. بقيت بقية رسالة المواصفات مقطوعة. أكدت إعادة الفحص أن `379cc71`
يحتوي SANAD داخلياً بلا جلسات أو واجهات حسابات. نحتفظ بـBetter Auth وPostgreSQL
وDrizzle وفق ADR-0004 ولا ننقل الهوية إلى مزوّد مُدار جديد.

## القرار

1. **Better Auth 1.7.23** مثبت بالنسخة، مع حزمة `@bahith/auth` مستقلة عن Next.js
   وDrizzle adapter بمعاملات فعلية وUUID. الجداول المنطقية تربط صراحةً إلى
   `users/sessions/accounts/verifications/two_factors/auth_rate_limits`.
2. **دور هوية مستقل `bahith_auth`:** بلا SUPERUSER أو BYPASSRLS أو صلاحيات إنشاء
   أدوار أو جداول، ولا يملك جداول أو وصولاً إلى البيانات البحثية. جداول الأسرار
   محمية بـFORCE RLS وسياسة الدور الخاص. دور البحث `bahith_app` يقرأ فقط ملف
   المستخدم المربوط عبر RLS، ولا يكتب الهوية ولا يصل للجلسات/كلمات المرور/2FA.
3. **فضاء شخصي ذري:** نُعدّل تفصيل hook الوارد في ADR-0004، لأن hook
   `user.create.after` في Better Auth 1.7 ينفذ بعد commit. بدلاً منه يشغّل INSERT
   المستخدم trigger ينشئ الفضاء وعضوية owner في المعاملة نفسها. مالكه دور
   `bahith_identity_provisioner` من نوع NOLOGIN بلا RLS bypass أو امتيازات هوية؛
   له فقط INSERT المطلوب في workspaces/memberships. يضبط سياق المعاملة ثم يعيده،
   مع `search_path = pg_catalog` وأسماء مؤهلة ومنع التنفيذ العام للدالة.
4. **دخول موثق:** البريد وكلمة المرور (12–128 محرفاً)، تحقق بريد إلزامي، واستعادة
   كلمة المرور مع إبطال الجلسات السابقة. Cookies خاصة بـBAHITH وHttpOnly وSameSite=Lax
   وSecure عند HTTPS؛ لا cookie cache للجلسة. لا ثقة بمعرّف مستخدم من العميل.
5. **TOTP ومفاتيح الاستعادة:** إضافة Better Auth الرسمية، وتأكيد الرمز قبل التفعيل.
   QR يولد محلياً. الأسرار ومفاتيح الاستعادة في حالة واجهة مؤقتة، ولا توضع في
   localStorage أو أدوات التتبع. يُختبر التفعيل وتحدي الدخول والتعطيل فعلياً.
6. **Google اختياري وصريح:** يظهر فقط عند ضبط المعرف والسر معاً. لأن TOTP المدمج
   لا يغطي OAuth افتراضياً، يمنع hook إنشاء جلسة Google لحساب فعّل TOTP المحلي
   ويوجهه لاستخدام كلمة المرور والعامل الثاني. لا نضيف دخول email-OTP يتجاوز TOTP.
   الربط الضمني للحسابات معطل، ولا نربط بريداً مختلفاً تلقائياً.
7. **Origin وCSRF:** لا تُعطّل فحوص المكتبة حتى في الاختبارات؛ تضبط القيمتان صراحةً
   إلى false. إضافة صغيرة ترفض origin المفقود/المختلف لكل طلب HTTP يغيّر الحالة،
   بما فيه أول دخول دون cookie. تستمر فحوص OAuth state/PKCE في المكتبة. البحث
   والمشاريع يتحققان من الجلسة الموثقة والعضوية والدور والمشروع معاً.
8. **حدود المعدل المشتركة:** جدول خاص في قاعدة البيانات؛ 100 طلب/دقيقة افتراضياً،
   و10 للدخول، و5 للتسجيل، و3 لطلب الاستعادة/إعادة التحقق. اختبار تكامل يثبت 429.
   عزل اختبارات المتصفح يمس صفوف قاعدة الاختبار المؤقتة فقط؛ السياسة تبقى مفعلة.
9. **البريد:** Nodemailer عبر SMTP مهيأ صراحةً، وTLS إلزامي للمضيف الخارجي عندما
   لا يكون SMTPS. محلياً Mailpit محصور بـ127.0.0.1 ويعرض الرسائل التجريبية؛ لا بريد
   حقيقياً يغادره. أخطاء البريد والمصادقة آمنة دون عناوين أو رموز أو SQL في السجلات.

## التوافق والهجرات

الهجرة 0004 إضافية مع down مختبَر. تشدد خصوصية users التي كانت ديناً موثقاً في
المرحلة الأولى. أُصلحت fixtures الاختبار لتنشئ الهوية بدور المصادقة والفضاء عبر
trigger الحقيقي؛ لم تُحفظ صلاحيات كتابة واسعة للتطبيق من أجل الاختبارات. لم تتغير
عقود health أو SANAD الداخلية. أُضيفت واجهات مشاريع واسترجاع HTTP بجلسة فعلية،
وبدون قبول userId من body، مع اختبارات عزل عبر المتصفح لمستخدمين مختلفين.

## البدائل والعواقب

- دور واحد للهوية والبحث يسهل الإعداد لكنه يسرّب أسرار الجلسات عند خطأ خدمة بحث.
- after-hook لا يضمن ذرية إنشاء الفضاء. دور provisioner الضيق يحافظ على FORCE RLS.
- واجهات حسابات بلا بريد فعلي/اختبار جلسة كانت ستترك المرحلة السابقة غير مكتملة.

الإعداد يضيف `AUTH_DATABASE_URL` و`BETTER_AUTH_SECRET/BETTER_AUTH_URL` وSMTP؛ يولد
bootstrap أسرار التطوير محلياً فقط. يتطلب Google مزوّداً وإعداداً حقيقيين قبل
اختبار الدخول الحي. هذه المرحلة لا تنفذ مزودات النماذج أو الرفع أو المحرر أو تصدير
البحث؛ يكملها طلب الاستكمال في الأجزاء التالية.
