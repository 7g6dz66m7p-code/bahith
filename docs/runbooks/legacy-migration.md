# دليل تشغيل: ترحيل منصة «باحث» القديمة — Legacy migration runbook

> الحزمة: `packages/migration` · الحالة: **تشغيل تجريبي (dry run) جاهز؛ التطبيق (apply) مختبر على Testcontainers فقط** ولا يُشغَّل على الإنتاج إلا بموافقة مكتوبة من صاحب المشروع.

## 1. ما الذي لا يُمَس أبداً

- المنصة القديمة `al-bahith.com` تبقى تعمل طوال الترحيل وبعده إلى أن يقرر صاحب المشروع غير ذلك.
- **لا** تغيير في DNS، **ولا** في Webhook بوت تيليجرام، **ولا** في بوابة الدفع أو إعداداتها أو اشتراكاتها المتكررة.
- **لا** كتابة في قاعدة البيانات القديمة: القارئ يتصل بنسخة قراءة فقط (read replica) بجلسة `default_transaction_read_only=on`، وكل صفحة تُقرأ داخل `BEGIN READ ONLY`.
- **لا** استدعاء لواجهات تيليجرام: جسر تيليجرام يتحقق محلياً من توقيع HMAC الذي أنشأه تيليجرام أصلاً.
- **لا** بيانات شخصية في التقارير: معرّفات قديمة، رموز أسباب، أعداد ومبالغ، وبريد مُقنَّع (`a***@d***.com`) عند الحاجة فقط.

## 2. ما يجب أن يقدّمه صاحب المشروع

1. **تفريغ المخطط** (schema only): `pg_dump --schema-only --no-owner` من قاعدة البيانات القديمة (أو ما يعادله إن لم تكن Postgres).
2. **رابط نسخة قراءة فقط** (`LEGACY_DATABASE_URL`) بمستخدم لديه `SELECT` فقط، يوضع في البيئة ولا يُرسل في المحادثة ولا يُكتب في ملف متتبَّع.
   - بديل: تصدير JSON بالشكل `{ "<table>": [ { "<column>": value } ] }`.
3. **ملف التعيين** `mapping.json` (نبنيه معاً من تفريغ المخطط): كل كيان → جدول قديم، وعمود المفتاح، وأعمدة الحقول، وخرائط القيم (مثل رموز الحالة).
   مثال كامل لمخطط **مُفترض** (ASSUMED، ليس المخطط الحقيقي): `packages/migration/fixtures/mapping.assumed.json`.
4. قائمة **رموز الخطط المجانية** وأسعار الخطط المدفوعة لكل عملة (لفحص الشذوذ المالي).
5. **رمز البوت** (`TELEGRAM_BOT_TOKEN`) للتحقق من التوقيعات فقط، عبر مدير الأسرار.
6. موافقة مكتوبة قبل كل من: التطبيق على بيئة staging، والتطبيق على الإنتاج، والتحويل النهائي.

## 3. الإجراء: تجربة ← مراجعة ← تطبيق ← تحقق ← تراجع

### 3.1 التشغيل التجريبي (لا يكتب شيئاً)

```bash
# من تصدير JSON
pnpm --filter @bahith/migration dry-run -- --source=json:./legacy-dump.json --mapping=./mapping.json --out=./out
# من نسخة القراءة (الرابط من البيئة فقط)
LEGACY_DATABASE_URL=... pnpm --filter @bahith/migration dry-run -- --source=postgres --mapping=./mapping.json --out=./out
```

المخرجات: `out/migration-report.json` و`out/migration-report.md`:

- الأعداد لكل كيان (مقروء / مقبول / مرفوض / متعارض) وملخص الأسباب.
- الصفوف المرفوضة والمتعارضة بمعرّفها القديم وأسبابها.
- **المطابقة المالية**: مجموع المدفوعات المسددة لكل عملة/شهر (بالوحدات الصغرى، دون أعداد عشرية عائمة)، وما طابق منها اشتراكاً وما لم يطابق، والمستردّات، وأيام الاشتراك المغطاة؛ قائمة المدفوعات غير المطابقة؛ ومفاتيح عدم التكرار (`payment:<provider>:<reference>`).

التقرير حتمي: المدخلات نفسها تعطي ملفاً مطابقاً بايتاً ببايت (عدا `generated_at`).

### 3.2 المراجعة (صاحب المشروع)

| السبب                                                            | المعنى                               | الإجراء المقترح                          |
| ---------------------------------------------------------------- | ------------------------------------ | ---------------------------------------- |
| `duplicate_email`                                                | بريد مكرر (دون اعتبار حالة الأحرف)   | يُدمج تلقائياً في الأقدم؛ ينقل أبناءه إليه |
| `same_email_different_phone` / `same_phone_different_email`      | هوية غامضة                           | قرار يدوي؛ لا دمج تلقائي                 |
| `missing_email`                                                  | مستخدم بلا بريد (غالباً تيليجرام فقط) | لا يُنشأ له حساب؛ يُقرَّر لاحقاً              |
| `payment_without_user`                                           | دفعة بلا مستخدم                      | مراجعة مالية قبل أي تطبيق                |
| `subscription_without_payment`                                   | اشتراك مدفوع بلا دفعة مسددة          | تأكيد من سجلات البوابة                   |
| `overlapping_period`                                             | فترتا اشتراك متداخلتان               | تحديد الفترة الصحيحة                     |
| `amount_outlier` / `amount_non_positive` / `invalid:amountMinor` | شذوذ مبلغ                            | مطابقة مع البوابة                        |
| `provider_reference_conflict`                                    | مرجع بوابة واحد بمبالغ مختلفة        | مراجعة مالية                             |

الصفوف المتعارضة **لا تُطبَّق** أبداً؛ تُصلح في المصدر أو في `mapping.json` ثم يُعاد التشغيل التجريبي.

### 3.3 التطبيق (Apply) — يتطلب موافقة مكتوبة

- **الحالة الحالية:** `applyPlan` مُنفَّذ ومُختبر على Testcontainers فقط، ولا يوجد أمر CLI له عمداً. تشغيله على staging/الإنتاج يحتاج: موافقة صاحب المشروع، وقرار المهندس الرئيسي بشأن تغييرات المخطط في `docs/migration/legacy-schema-requests.md`، واتصال مشغّل يملك مخطط `bahith_migration`.
- الهويات تُنشأ عبر دور المصادقة الخاص `bahith_auth` (كما تفعل خدمة المصادقة)، والمشغّل `users_personal_workspace` ينشئ الفضاء الشخصي والعضوية ذرّياً. البريد يُنشأ **غير مؤكد**؛ يدخل المستخدم بعد «استعادة كلمة المرور».
- إن كان البريد مسجلاً مسبقاً في المنصة الجديدة: **تخطٍّ** (`email_exists_in_target`)، لا دمج تلقائي (خطر الاستيلاء على حساب).
- المشاريع عبر `withWorkspaceMember` بدور التطبيق `bahith_app` (RLS مفروضة)؛ الاشتراك الأحدث فقط لكل فضاء (المخطط الحالي يسمح باشتراك واحد).
- المدفوعات ومراجع الملفات: **مؤجلة** (`deferred`) لعدم وجود جداول هدف؛ روابط تيليجرام تُحفظ في سجل الترحيل.
- **عدم التكرار:** سجل `bahith_migration.items` بمفتاح (الكيان، المعرّف القديم)، ومعرّف الهدف يُحجز قبل الكتابة، فإعادة التشغيل لا تنشئ شيئاً مرتين حتى بعد انقطاع بين الكتابة وتحديث السجل.
- **الاستئناف:** نقطة تفتيش لكل دفعة (`checkpoints`)؛ `applyPlan(plan, targets, { runId })` بالمعرّف نفسه يكمل من حيث توقف.

### 3.4 التحقق

1. أعد التشغيل التجريبي، وقارن أعداد المقبول مع `ApplySummary.created + alreadyPresent`.
2. أعد `applyPlan` بمعرّف تشغيل جديد: يجب أن تكون كل قيم `created` صفراً.
3. عيّنة يدوية (10 مستخدمين) يراجعها صاحب المشروع: الفضاء، المشاريع، الاشتراك.
4. اختبار العزل الحالي (`pnpm test:integration`) يبقى أخضر.

### 3.5 التراجع

- كل صف مُنشأ موسوم بمعرّف التشغيل في السجل. `rollbackRun(runId, targets)` يحذف الفضاءات الشخصية التي أنشأها التشغيل (تتبعها المشاريع والاشتراكات والعضويات بالتتالي) ثم الهويات، ثم ينسى صفوف السجل.
- **آمن فقط قبل التحويل النهائي.** بعده قد يكون المستخدمون أضافوا بياناتهم؛ التراجع حينها = استعادة النسخة الاحتياطية (`docs/runbooks/backup-restore.md`) بقرار صاحب المشروع.
- خذ نسخة احتياطية (`pnpm db:backup`) قبل كل تطبيق.

## 3أ. من ملف `u747978280_bahith.sql` مباشرة (أُضيف 2026-11-25)

الملف يبقى **خارج المستودع** (مثلاً `/secure/legacy/`) وكل المخرجات كذلك.

1. **بصمة الملف (نسخة احتياطية مرجعية):**
   `sha256sum u747978280_bahith.sql` واحفظ الملف والبصمة في مكانين منفصلين قبل أي خطوة.
2. **فحص البنية الحقيقية** (حاوية MariaDB مؤقتة تُحذف بعده؛ بلا محتوى صفوف في التقرير):
   ```bash
   pnpm --filter @bahith/migration inspect-dump -- --dump=/secure/legacy/u747978280_bahith.sql --out=/secure/legacy/report
   ```
   يعطي: الجداول، الأعمدة وأنواعها، المفاتيح، العلاقات المعلنة وغير المعلنة (`*_id`)، الصفوف اليتيمة، وأعداد الصفوف.
3. **كتابة ملف الربط** (`mapping.json`) من التقرير لا من التخمين — جدولاً جدولاً مع صاحب المشروع.
   **سؤال يجب حسمه من البيانات:** أعمدة `DATETIME` في MySQL بلا منطقة زمنية؛ المحرك يعدّها UTC. نقارن
   أوقاتاً معروفة (مثل آخر تسجيل) قبل الاعتماد، ونضبط الربط إن كان الخادم القديم على توقيت آخر.
4. **Dry Run من الملف نفسه** (قراءة فقط داخل `START TRANSACTION READ ONLY`):
   ```bash
   pnpm --filter @bahith/migration dry-run -- --source=dump:/secure/legacy/u747978280_bahith.sql \
     --mapping=/secure/legacy/mapping.json --out=/secure/legacy/dry-run
   ```
   تقرير المطابقة: لكل كيان المقروء/المقبول/المرفوض/المتعارض، وأسباب كل رفض (مثل `missing_email`،
   `subscription_without_payment`)، ومطابقة مالية (مجموع المدفوعات بالعملة قبل وبعد).
5. **قبل أي تطبيق على Staging:** تشغيل workflow ‏`Database backup and restore test → staging`
   (نسخة + استعادة مُتحقق منها). ثم التطبيق على Staging فقط، ثم `verify-deployment --isolation-smoke`.
6. **التراجع:** `rollbackRun` يحذف كل ما أنشأه تشغيل الترحيل بمعرّفه (قبل التحويل فقط)، وإلا الاستعادة
   من النسخة الاحتياطية للخطوة 5. الإنتاج لا يُمس إلا بموافقة منفصلة مكتوبة.

مختبر على تفريغ اصطناعي (`fixtures/legacy-mysql.synthetic.sql`): 4 اختبارات تكامل (البنية، عدم تسريب
المحتوى، القراءة فقط مع العربية، Dry Run بأسباب الرفض).

## 4. التحويل دون توقف (المنصة القديمة تبقى تعمل)

1. **التطبيق الأولي** على الإنتاج الجديد (بعد الموافقة) بينما القديمة تعمل كالمعتاد. لا يُعلَن عن المنصة الجديدة بعد.
2. **مزامنة الفروق** بشكل دوري: `dry-run --since=<آخر تشغيل>` (تُقرأ الصفوف ذات `updated_at` الأحدث فقط) ثم تطبيق المقبول. الكيانات المتغيرة بعد ترحيلها تُراجع يدوياً (التطبيق لا يحدّث صفاً موجوداً).
3. **نافذة التجميد** (يحددها صاحب المشروع، قصيرة): إيقاف التسجيل والدفع الجديد في المنصة القديمة **من قِبل صاحب المشروع وبأدواته هو**، ثم مزامنة فروق أخيرة ومطابقة مالية نهائية (مجموع المدفوعات لكل عملة/شهر يطابق تقرير البوابة).
4. **التحويل النهائي** — بموافقة صاحب المشروع فقط: صاحب المشروع (لا هذه الأداة) يوجّه المستخدمين إلى المنصة الجديدة. DNS وWebhook البوت والبوابة تبقى دون تغيير من جهتنا؛ أي تغيير فيها قرار وتنفيذ منفصل لصاحب المشروع.
5. المنصة القديمة تبقى للقراءة إلى أن يقرر صاحب المشروع إيقافها.

## 5. جسر تيليجرام

- `verifyLoginWidget(fields, config)` و`verifyWebAppInitData(initData, config)`: HMAC-SHA256 حسب وثائق تيليجرام، مقارنة ثابتة الزمن، وحد أقصى لعمر `auth_date` (افتراضياً يوم؛ `TELEGRAM_AUTH_MAX_AGE_SECONDS`).
- `linkTelegramAccount(verified, store)` يربط معرّف تيليجرام المتحقَّق منه بمستخدم مُرحَّل عبر روابط الترحيل. **الربط وحده ليس جلسة دخول**: يجب أن يكون المستخدم مسجلاً الدخول في حسابه الجديد (أو أثبت بريده) قبل اعتماد الربط.

## English summary

- **Never touched:** the legacy platform, its DNS, the Telegram webhook, the payment gateway. Legacy reads are server-enforced read-only; no Telegram API calls.
- **Owner provides:** schema dump, read-only replica URL (env only) or JSON export, `mapping.json`, free plan codes and prices, bot token (for signature checks only), written approvals.
- **Procedure:** dry run (deterministic JSON + Markdown report, financial reconciliation, no personal data) → owner review of conflicts → apply (test-only today; needs approval and the lead's schema decision) → verify (re-run is a no-op) → rollback by run id (pre-cut-over only).
- **Cut-over:** initial load while legacy runs → delta syncs by `updated_at` (`--since`) → short freeze window operated by the owner → final delta + reconciliation → switch only with owner approval.
